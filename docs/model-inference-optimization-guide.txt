# Support optimized multi graph

For now, every model is an init graph and an exec graph. 
Instead let’s support graph with multiple entry-points (multiple exec phase). 
A common use case for this is when you have different compiles graphs you want to run for one model (eg diffuser and LLM).
Another interesting use case would be to have one graph for decode, one for refill. I don’t know if it would help that much since you seem to run different kernels already with prefill vs decode thanks to runtime if / else based on shapes, but maybe you could do more with that.

The way it should be done, there is a single init phase, but multiple exec (entry points). This way multiple entries points should share weights (or anything else).
This must be done in a way that doesn’t explode memory size of course. 
Memory planning should be very smart about it.
You can assume 2 execs won’t run ever in parallel, so memory planning must be able to shape buffers / allocation between multiple graph to minimize the total allocated size.

I mentioned prefill / decode graph split, but it was just an idea, maybe even better things / different graph splits could be done to improve performance.

Start by implementing the feature with basic unit and end to end tests, then use it to try and optimize models.

# General graph break avoidance / dynamic shape optimization

Graph breaks are terrible, they happens when we can’t encode all the model at once, and we need to execute some code on CPU, having to stop and sync.
It could be for multiple reasons:
1. some ops aren’t supported on GPU or run faster on CPU.
2. Some ops have dynamic / data dependent shapes and we can’t allocate some buffers / execute them without a graph break

Usually 1 is rare but can’t really be avoided.
But 2 is the biggest problem.

Think about it, if you were writing the whole forward pass manually without the compiler / runtime, being fully flexible, would you be able to get rid of some (or all) of these graph breaks ? If yes, that means the compiler, runtime, model must be updated somehow to fix it and get the same results.

Some ideas:
- There is always a graph break already: between each forward pass. Maybe some of the CPU code could be moved to run at the beginning or end of the forward pass instead.
- The graph could potentially be rewritten to get rid of these CPU ops / break or move them to a better place. 
- The parametric dimension system could be extended to support more operations, and / or maybe the graph could be updated to turn data-dependent shapes into smarter parametric ones.
- Maybe more kernel fusion or smarter buffer allocation could help somehow sometimes ?

These are just ideas ideas, but I believe if manually you could write the model without these graph breaks, you should find a way to do the same with lokinfer, whatever that is.

# General init time optimization

Look at the IR and investigate, are there any ops that should run during model setup (init graph) but are still in exec ? 
If yes, investigate why they are not moved and fix it.
Maybe also in some cases the graph could be rewritten also to move even more ops to init (this is not always possible / straightforward, and should only be done when it really does improve performance in the end).
Eg: you could run the broadcast of a constant in init, but almost always you wouldn’t want to do so, since this broadcast is fused with other things, and materializing the full tensor would give worst performance.

# General I/O kernels static spec optimization

One problem I used to have a lot with fused kernels, is that to generate efficient code, we need to know the static shape / strides / alignment of the buffers to be able to generate simpler index computations but also to always vectorize load / store when possible. 
This was mostly a problem because kernels were automatically fused by a compiler.

I have no idea if the same issue could arise with manually fused kernels.

But in general, when investigating / optimizing the performance of fused kernels, especially when it involves fused view operations like transpose, reshape, broadcast, slice etc, we need to make sure all of this is optimal:
- Are they some scalar load / store where we could use vector (or larger vector size) operations instead ?
- Is the index computation optimal ? Tensor are N-D but it’s all linear. Maybe we could flatten index computation more / entirely, factor out some index computation ? Also divide / mod are terrible and should be replaced with binary operations as much as possible.

This requires lots of profiling anyway to figure out and fix those issues.

# General kernel performance optimization

This doesn’t just apply to qwen, the question is in general how we can profile / optimize / fine tune some kernels on some specific shapes to get the best possible performance for that kernel.

Again I’m really not an expert for this, but here are some suggestions I can give you:
- Really optimize a kernel when it’s really gonna help the performance E2E. It’s a mix of how much of the total % exec time this kernel corresponds to, and how much improvement you think you can get. It’s not worth optimizing a kernel taking 0.01% of total exec time, even if you make it 100 times faster. Also a kernel taking 1% but that could only again 5% perf max isn’t going to help that much either (these are just random numbers, don’t take them as rules).
- Optimize the kernel first on the most relevant / important shapes. Having E2E testing and / or real life input / usage would help you get those actual real shapes.
- Have a great way to infer the max theoretical  (or even real) performance of a kernel. This way you could directly know how far you are, and if it’s even worth optimizing it or not.
- Beside the previous point, if you can have actual reference fully optimized kernels for this kernel, then you can you know for sure that if they can make it that fast, so can you (or even faster).
- It’s even better if you can have the source code of these kernels. It would give you a lot more information as well as trick / strategies to optimize your kernel and learn / reproduce them.
- In general, having multiple libraries of available highly optimized ML kernels for Apple GPUs would help a lot. Even if these aren’t the same kernels, looking at them / profiling them could help you learn and understand new strategies to optimize your own kernels.
- Also for better performance don’t hesitate to have different kernels for different shapes / devices. We already usually have some different kernels sometimes for prefill vs decode, but we can also split more depending on the shapes in general and run different kernels. Also thanks to finetuning kernels should also have different parameters depending on the shape too. This ensures we can optimize kernels independently for different shapes / dtypes.
- Also, as much as possible, when beneficial, use parametric / compile time / templated values, unrolled loops, etc. This might require some big dynamic if / else that calls the static templated kernels, and might make compile time slower, but if in the end it gives a big performance improvement it’s worth it.
- Play with the shader compiler flag options / math modes, function constants vs templates, etc. this might sometimes lead to some performance improvements too for some kernels.
- Have a strong, flexible and efficient auto-tuning infrastructure to search and find automatically the best kernel parameters per shape / device.
- Finally, I suggest having some list of strategies and / or some recipes you can use for profiling / experimenting / finetuning kernels in general, to know exactly what to look for and to do it better and more efficiently.

Again, I repeat I’m not the expert on that, use your own judgment, and find all available source code and resources you can online that help you write the most possible optimized kernels.
